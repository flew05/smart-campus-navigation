2.1 & 2.2 FUNCTIONAL AND NON-FUNCTIONAL REQUIREMENTS
----------------------------------------------------

The system requirements are organized in Table 1 below, showing traceability to identified problems and priority levels.

Table 1: System Requirements

Functional Requirements:

FR1: The system shall allow users to search for campus locations by name, building code, or room number.
Type: Functional
Addresses: Problem 1 (Navigation Confusion)
Priority: High
Justification: Essential for users to find destinations before navigation can begin.

FR2: The system shall calculate optimal routes between two campus locations, including outdoor paths and indoor corridors.
Type: Functional
Addresses: Problem 1 (Navigation Confusion)
Priority: Critical
Justification: Core navigation functionality directly addressing navigation confusion and tardiness.

FR3: The system shall integrate with the university's schedule management system to automatically retrieve users' class schedules.
Type: Functional
Addresses: Problem 2 (Lack of Real-Time Information)
Priority: Critical
Justification: Enables schedule-based routing and proactive notifications. Centralizes fragmented information.

FR4: The system shall provide turn-by-turn navigation instructions with visual, text, and optional audio guidance.
Type: Functional
Addresses: Problem 1 (Navigation), Problem 3 (Accessibility)
Priority: High
Justification: Supports diverse user preferences and accessibility needs.

FR5: The system shall display real-time room availability status for classrooms, study spaces, and computer labs.
Type: Functional
Addresses: Problem 2 (Lack of Real-Time Information)
Priority: High
Justification: Addresses lack of real-time facility information, improves space utilization.

FR6: The system shall send push notifications to users about schedule changes, room reassignments, and campus events.
Type: Functional
Addresses: Problem 2 (Lack of Real-Time Information)
Priority: Critical
Justification: Prevents students from missing classes due to last-minute changes.

FR7: The system shall calculate and display accessible routes that avoid stairs and include elevator locations.
Type: Functional
Addresses: Problem 3 (Accessibility Barriers)
Priority: Critical
Justification: Required for ADA compliance. Addresses accessibility barriers directly.

FR8: The system shall support voice-based navigation commands and provide compatibility with screen reader software.
Type: Functional
Addresses: Problem 3 (Accessibility Barriers)
Priority: High
Justification: Enables independent navigation for visually impaired users.

FR9: The system shall allow faculty and staff to update room information, office hours, and send location-specific announcements.
Type: Functional
Addresses: Problem 2 (Lack of Real-Time Information)
Priority: Medium
Justification: Ensures data accuracy and enables timely communication with students.

FR10: The system shall provide a guest mode that allows navigation without user authentication for campus visitors.
Type: Functional
Addresses: Problem 1 (Navigation Confusion)
Priority: High
Justification: Serves visitor needs without creating barriers to entry. Security: read-only access to public information only.

FR11: The system shall display the user's current location on an interactive campus map with zoom and pan capabilities.
Type: Functional
Addresses: Problem 1 (Navigation Confusion)
Priority: Critical
Justification: Provides spatial context necessary for effective navigation.

FR12: The system shall save frequently visited locations and recent searches for quick access.
Type: Functional
Addresses: Problem 1 (Navigation Confusion)
Priority: Low
Justification: Improves user efficiency and reduces repetitive data entry.

FR13: The system shall automatically suggest navigation to the next class 15 minutes before scheduled start time based on user's integrated schedule.
Type: Functional
Addresses: Problem 1 (Navigation), Problem 2 (Missed Classes)
Priority: High
Justification: Proactive navigation alerts prevent tardiness and forgotten classes. Implementation: System sends notification "Your next class starts in 15 minutes. Navigate now?" with one-tap navigation launch.


Non-Functional Requirements:

NFR1: Performance - Route Calculation Speed
The system shall calculate routes within 3 seconds for 95% of requests under normal network conditions.
Addresses: Problem 1 (Navigation Confusion)
Priority: Critical
Justification: Users need quick responses when navigating between classes with limited time. Delays cause frustration and defeat the purpose of reducing tardiness.

NFR2: Availability
The system shall maintain 99.5% uptime during academic hours (7 AM - 10 PM, Monday-Friday).
Addresses: Problem 1, Problem 2
Priority: Critical
Justification: System unavailability during class transitions would severely impact users who depend on it for navigation. Critical for trust and adoption.

NFR3: Usability - Learnability
New users shall be able to successfully navigate to a destination within 2 minutes of first using the application, without training.
Addresses: Problem 1 (Navigation Confusion)
Priority: High
Justification: Student population includes new users each semester. Complex interfaces would create barriers and reduce adoption.

NFR4: Accessibility - WCAG Compliance
The system shall comply with WCAG 2.1 Level AA standards for web and mobile accessibility.
Addresses: Problem 3 (Accessibility Barriers)
Priority: Critical
Justification: Legal requirement (ADA) and ethical obligation. Ensures equitable access for students with disabilities.

NFR5: Security - Data Privacy and Access Control
The system shall encrypt all user location data and schedule information using TLS 1.3 during transmission and AES-256 at rest.
Access Control:
- Authenticated Users: Full access to personalized features (schedule, booking, notifications, history)
- Guest Mode: Read-only access to public information only (map, building locations, basic navigation). Cannot access: room availability details, schedule integration, booking systems, or user-specific data.
Addresses: Data Privacy, Security Concerns
Priority: Critical
Justification: Location and schedule data are sensitive personal information. University must comply with FERPA and protect student privacy. Guest mode limitations prevent unauthorized access to academic information while serving visitors.

NFR6: Reliability - Positioning Accuracy
The system shall maintain positioning accuracy within 5 meters outdoors (GPS) and 3 meters indoors (beacon-based).
Addresses: Problem 1 (Navigation Confusion)
Priority: High
Justification: Insufficient accuracy would result in incorrect directions, particularly problematic in large buildings with similar corridors.

NFR7: Performance - Battery Efficiency
The application shall consume no more than 5% of device battery per hour of active navigation.
Addresses: User Experience
Priority: Medium
Justification: Excessive battery drain would discourage users from keeping the app active, reducing its utility for continuous navigation throughout the day.


Requirements Traceability Matrix:

Problem 1 (Navigation Confusion) → FR1, FR2, FR4, FR10, FR11, FR12, FR13 + NFR1, NFR3, NFR6
Problem 2 (Real-Time Information) → FR3, FR5, FR6, FR9, FR13 + NFR2
Problem 3 (Accessibility Barriers) → FR4, FR7, FR8 + NFR4
Security & Privacy → FR10, NFR5


2.3 EXPLANATORY NOTE (≤1 page)
-------------------------------

The requirements were derived through systematic analysis of the three core problems identified in Task 1 and aligned with stakeholder expectations.

Functional requirements prioritize:
1. Navigation precision (FR1-FR4, FR11, FR13) - Addresses Problem 1 through accurate, multi-modal routing with proactive schedule-based alerts
2. Information integration (FR3, FR5, FR6, FR9) - Solves Problem 2 by centralizing fragmented campus data
3. Accessibility (FR4, FR7, FR8) - Tackles Problem 3 by embedding inclusive design from the start

The guest mode (FR10) recognizes that visitors represent a significant user group whose positive experience impacts university reputation and recruitment. However, NFR5 clarifies that guest access is restricted to public information only, preventing security concerns about unauthorized access to academic data.

FR13 was added to address automatic schedule-based navigation—a proactive feature that reduces tardiness by alerting students 15 minutes before class starts. This directly implements the "schedule integration" capability described in the system overview.

Non-functional requirements balance performance with resource constraints. The 3-second route calculation target (NFR1) is based on UX research showing users tolerate 2-4 seconds for navigation queries. The 99.5% uptime (NFR2) allows for approximately 30 minutes of downtime per week, suitable for maintenance windows outside peak hours.

Accessibility compliance (NFR4) goes beyond legal minimums because navigation directly impacts independence and safety. Location accuracy (NFR6) thresholds are based on typical campus architecture—5 meters outdoors distinguishes between building entrances, while 3 meters indoors differentiates adjacent rooms.

The requirements collectively create a system that is not merely a digital map but an intelligent navigation companion integrated into the daily campus experience, with appropriate security controls to protect sensitive student data while remaining accessible to visitors.
