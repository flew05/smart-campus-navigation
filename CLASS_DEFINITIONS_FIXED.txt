5.2 CLASS DEFINITIONS (≤2 pages)
---------------------------------

USER
Purpose: Represents system users (Student, Visitor, Faculty/Staff)
Attributes: userID, name, email, role, isAuthenticated
Operations: login(), logout(), updateProfile(), setPreferences()
Relationships: Has Schedule (1:1), Receives Notification (1:0..*)
Responsibilities: Authentication, profile management, preference configuration

SCHEDULE
Purpose: Contains user's academic schedule with class sessions
Attributes: scheduleID, courseName, time, date
Operations: getNextClass(), getClassByTime(), updateSchedule()
Relationships: Belongs-to User (1:1), Held-in Location (1:1)
Responsibilities: Retrieve upcoming classes, integrate with university schedule system, provide class location information

LOCATION
Purpose: Represents physical places on campus (room, entrance, landmark)
Attributes: locationID, name, floor, coordinates
Operations: getCoordinates(), calculateDistance(), isAccessible()
Relationships: Used-by Schedule (1:*), Referenced-by NavigationService
Responsibilities: Store coordinates, distance calculations, accessibility indication, provide spatial information

NAVIGATIONSERVICE
Purpose: Core service calculating routes and providing real-time navigation
Attributes: currentRoute, isNavigating
Operations: calculateRoute(), updateRoute(), getCurrentPosition(), provideGuidance()
Relationships: Uses CampusMap, Interacts-with Location, Serves User
Responsibilities: Pathfinding algorithm, position tracking, guidance generation, real-time route updates

CAMPUSMAP
Purpose: Geographic data representation of campus
Attributes: mapVersion, lastUpdate, zoomLevel
Operations: getMapData(), updateMap(), findLocation(), showRoute()
Relationships: Used-by NavigationService, Contains Location data
Responsibilities: Store map data, display routes, enable location search, provide geographic context

NOTIFICATION
Purpose: System messages to users (alerts, reminders, announcements)
Attributes: notificationID, title, message, timestamp, priority, type, isRead
Operations: send(), markAsRead(), dismiss()
Relationships: Received-by User (*:*)
Responsibilities: Message delivery, read tracking, priority management, event notifications

Design Decisions:
- User-Schedule relationship: One-to-one relationship enables personalized schedule integration for authenticated users
- NavigationService as central coordinator: Implements Facade pattern, hides pathfinding complexity, coordinates between map data and user location
- Notification independence: Allows multiple sources (schedule changes, room updates, events) without tight coupling to other system components
- Location centralization: Single Location class serves both schedule management and navigation, reducing data duplication
- CampusMap separation: Isolates geographic data management from navigation logic, allowing independent updates to campus infrastructure
