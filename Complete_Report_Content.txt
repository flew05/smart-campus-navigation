1.1 SYSTEM DESCRIPTION
----------------------

System Name: Smart Campus Navigation System (SCNS)

Purpose:
The Smart Campus Navigation System is designed to eliminate navigation challenges faced by students, visitors, and staff on an expanding university campus. The system provides real-time indoor and outdoor navigation, integrates with academic schedules, displays facility availability, and ensures accessibility for users with disabilities.

Target Users:
- Primary: Students (new and continuing)
- Secondary: Campus visitors (prospective students, parents, guests)
- Tertiary: Faculty and staff members
- Accessibility users: Students with mobility, visual, or hearing impairments

Main Functionalities:
1. Real-time Navigation: Indoor and outdoor routing with multi-floor support
2. Schedule Integration: Automatic route generation based on class schedules
3. Room Availability: Display of classroom, study space, and office availability
4. Notifications: Event announcements, schedule changes, room reassignments
5. Accessibility Features: Voice navigation, screen reader support, step-free routes
6. Search & Discovery: Location search for buildings, rooms, facilities, and amenities
7. Map Visualization: Interactive campus map with real-time user location

Context of Use:
The system operates as a mobile application (iOS/Android) used primarily on-campus but accessible from anywhere. Users interact with it while walking between classes, searching for meeting locations, finding study spaces, or navigating to campus events. The system requires GPS for outdoor navigation, indoor positioning technology (Wi-Fi/Bluetooth beacons) for indoor navigation, and integration with university information systems (schedule database, room booking system, event management).

1.3 PROBLEM DEFINITION
----------------------

Problem 1: Navigation Confusion and Tardiness

Description: 
Students and visitors frequently get lost on campus, especially during the first weeks of the semester or when room assignments change. The expanding campus with new buildings exacerbates this issue. Current solutions (static maps, signage) are insufficient for a dynamic campus environment.

Impact: 
Students arrive late to classes, miss important meetings, and experience stress and frustration. Faculty report delays at the start of classes. Prospective students may form negative impressions during campus visits.

Stakeholders Affected: Students, Visitors, Faculty


Problem 2: Lack of Real-Time Facility Information

Description: 
Students waste significant time searching for available study spaces, computer labs, or open classrooms. There is no centralized system showing real-time room availability or last-minute room changes. Email notifications about changes are often missed or seen too late.

Impact: 
Inefficient use of campus facilities, student frustration, missed classes due to unnoticed room changes, reduced productivity.

Stakeholders Affected: Students, Faculty, Campus Administration


Problem 3: Accessibility Barriers

Description: 
Students with disabilities face significant challenges navigating campus independently. Current maps don't indicate accessible routes, elevator locations, or step-free paths. Navigation tools are not compatible with screen readers and assistive technologies.

Impact: 
Limited independence for students with disabilities, potential ADA compliance issues, inequitable campus experience.

Stakeholders Affected: Students with Disabilities, Campus Administration


Problem 4: Information Fragmentation

Description: 
Campus information is scattered across multiple platforms—class schedules in one system, building maps on the website, event notifications via email, room availability through separate booking systems. Users must navigate multiple interfaces to plan their campus activities.

Impact: 
Cognitive overload, missed events, inefficient time management, reduced engagement with campus activities.

Stakeholders Affected: Students, Visitors, Faculty

2. SYSTEM REQUIREMENTS
===============================================================================

2.1 FUNCTIONAL REQUIREMENTS
----------------------------

FR1: The system shall allow users to search for any campus location by name, building code, or room number.

Justification: Essential for users to find their destination before navigation can begin. Supports all primary use cases.


FR2: The system shall calculate optimal routes between two campus locations, including both outdoor paths and indoor corridors.

Justification: Core navigation functionality addressing Problem 1 (navigation confusion).


FR3: The system shall integrate with the university's schedule management system to automatically retrieve and display users' class schedules.

Justification: Enables schedule-based routing and proactive notifications. Addresses Problem 4 (information fragmentation).


FR4: The system shall provide turn-by-turn navigation instructions with visual, text, and optional audio guidance.

Justification: Supports diverse user preferences and accessibility needs (Problem 3).


FR5: The system shall display real-time room availability status for classrooms, study spaces, and computer labs.

Justification: Directly addresses Problem 2 (lack of real-time facility information). Improves space utilization.


FR6: The system shall send push notifications to users about schedule changes, room reassignments, and campus events relevant to their location or schedule.

Justification: Prevents students from missing classes due to last-minute changes. Addresses Problem 2.


FR7: The system shall calculate and display accessible routes that avoid stairs and include elevator locations for users with mobility impairments.

Justification: Required for ADA compliance and addresses Problem 3 (accessibility barriers).


FR8: The system shall support voice-based navigation commands and provide compatibility with screen reader software.

Justification: Enables independent navigation for visually impaired users. Addresses Problem 3.


FR9: The system shall allow faculty and staff to update room information, office hours, and send location-specific announcements.

Justification: Ensures data accuracy and enables timely communication with students.


FR10: The system shall provide a guest mode that allows navigation without user authentication for campus visitors.

Justification: Serves secondary stakeholder needs (visitors) without creating barriers to entry.


FR11: The system shall display the user's current location on an interactive campus map with zoom and pan capabilities.

Justification: Provides spatial context necessary for effective navigation. Fundamental mapping feature.


FR12: The system shall save frequently visited locations and recent searches for quick access.

Justification: Improves user efficiency and reduces repetitive data entry.


2.2 NON-FUNCTIONAL REQUIREMENTS
--------------------------------

NFR1: Performance - Route Calculation Speed

The system shall calculate routes within 3 seconds for 95% of requests under normal network conditions.

Justification: Users need quick responses when navigating between classes with limited time. Delays cause frustration and defeat the purpose of reducing tardiness.


NFR2: Availability

The system shall maintain 99.5% uptime during academic hours (7 AM - 10 PM, Monday-Friday).

Justification: System unavailability during class transitions would severely impact users who depend on it for navigation. Critical for trust and adoption.


NFR3: Usability - Learnability

New users shall be able to successfully navigate to a destination within 2 minutes of first using the application, without training.

Justification: Student population includes new users each semester. Complex interfaces would create barriers and reduce adoption.


NFR4: Accessibility - WCAG Compliance

The system shall comply with WCAG 2.1 Level AA standards for web and mobile accessibility.

Justification: Legal requirement (ADA) and ethical obligation. Ensures equitable access for students with disabilities.


NFR5: Security - Data Privacy

The system shall encrypt all user location data and schedule information using TLS 1.3 during transmission and AES-256 at rest.

Justification: Location data is sensitive personal information. University must comply with FERPA and protect student privacy.


NFR6: Reliability - Positioning Accuracy

The system shall maintain positioning accuracy within 5 meters outdoors (GPS) and 3 meters indoors (beacon-based).

Justification: Insufficient accuracy would result in incorrect directions, particularly problematic in large buildings with similar corridors.


NFR7: Performance - Battery Efficiency

The application shall consume no more than 5% of device battery per hour of active navigation.

Justification: Excessive battery drain would discourage users from keeping the app active, reducing its utility for continuous navigation throughout the day.


2.3 EXPLANATORY NOTE
---------------------

The requirements were derived through systematic analysis of the four core problems identified in Task 1 and aligned with stakeholder expectations.

Functional requirements prioritize three key capabilities:

1. Navigation precision (FR1-FR4) - Directly addresses Problem 1 by providing accurate, multi-modal routing

2. Information integration (FR3, FR5, FR6) - Solves Problem 2 and Problem 4 by centralizing fragmented campus data

3. Accessibility (FR7, FR8) - Tackles Problem 3 by embedding inclusive design from the start

The guest mode (FR10) recognizes that visitors represent a significant but often overlooked user group whose positive experience impacts university reputation and recruitment.

Non-functional requirements balance performance with resource constraints. The 3-second route calculation target (NFR1) is based on UX research showing users tolerate 2-4 seconds for navigation queries. The 99.5% uptime (NFR2) allows for approximately 30 minutes of downtime per week, suitable for maintenance windows outside peak hours.

Accessibility compliance (NFR4) goes beyond legal minimums because navigation is a domain where accessibility directly impacts independence and safety. Location accuracy (NFR6) thresholds are based on typical campus architecture—5 meters outdoors distinguishes between building entrances, while 3 meters indoors differentiates adjacent rooms.

The requirements collectively create a system that is not merely a digital map but an intelligent navigation companion integrated into the daily campus experience.

3.2 EXPLANATORY NOTE
--------------------

System-Level Functional Decomposition

The FFBD represents the complete functional flow of the Smart Campus Navigation System, decomposing high-level operations into executable sub-functions while showing their logical sequence, decision points, and parallel execution opportunities.

Function Hierarchy and Rationale:

LEVEL 0: PRIMARY FUNCTIONS (1.0 - 9.0)

Function 1.0 - Launch Mobile App: 
The entry point that initializes the application environment, loads cached data, and prepares the user interface. This function is critical for performance (NFR1) as it impacts perceived responsiveness.

Function 2.0 - Authenticate User: 
Implements user verification with decision logic. The system supports both authenticated (students/faculty) and guest modes, addressing FR10. Authentication success determines access to personalized features (schedule integration, saved locations).

Function 2.1 - Use Guest Mode: 
Parallel path for unauthenticated users (visitors). This ensures the system remains accessible without creating barriers to entry, supporting the visitor stakeholder group.

Function 3.0 - Retrieve User Context: 
Aggregates personalized data (current location, class schedule, preferences) from multiple sources. This function integrates with university systems (FR3) and is foundational for intelligent routing.

Function 4.0 - Select Destination: 
Captures user intent through search (FR1), schedule selection, or map interaction. This is the primary user input point that drives subsequent navigation functions.

PARALLEL EXECUTION BLOCK (5.0 & 6.0):

The FFBD shows parallelism between route calculation and room availability checking. These functions can execute concurrently because they query different data sources and have no sequential dependency. This design decision improves performance by reducing total processing time.

Function 5.0 - Calculate Route: 
Core navigation logic implementing FR2. Decomposes into:
- 5.1 Apply Accessibility Preferences: Conditionally modifies route constraints (FR7) based on user profile
- 5.2 Generate Turn-by-Turn Instructions: Produces human-readable guidance (FR4)

Function 6.0 - Check Room Availability: 
Implements FR5, decomposed into:
- 6.1 Query Room Database: Retrieves current booking status
- 6.2 Update Availability Status: Refreshes display with real-time data

Function 7.0 - Display Navigation: 
Renders route on interactive map (FR11) with multimodal output (visual, text, audio per FR4, FR8).

Function 8.0 - Provide Real-Time Updates: 
Continuous monitoring function that detects route deviations, schedule changes, or room reassignments, triggering FR6 notifications.

Decision Point - User Reached Destination?: 
Creates feedback loop. If user has not reached destination, system continues real-time updates (Function 7.0-8.0 loop). This iterative structure supports dynamic navigation adjustments.

Function 9.0 - Send Notifications if Needed: 
Final opportunistic function that delivers any pending announcements or follow-up information before session termination.

CONTROL LOGIC RATIONALE:

1. Sequence: The primary flow is sequential where data dependencies exist (must authenticate before retrieving user context)

2. Parallelism: Functions 5.0 and 6.0 execute concurrently to optimize performance (NFR1)

3. Iteration: The loop from decision point back to 7.0 represents continuous navigation tracking

4. Conditional Branching: Authentication decision enables two valid paths (authenticated vs. guest), making the system flexible

This decomposition ensures all functional requirements (FR1-FR12) are addressed through specific functions while maintaining logical coherence and supporting non-functional requirements for performance and usability.

4.2 DETAILED USE CASE DESCRIPTIONS
-----------------------------------

USE CASE 1: NAVIGATE TO LOCATION

Title: Navigate to Location

Primary Actor: Student

Stakeholders and Interests:
- Student: Wants quick, accurate route to classroom/facility
- Campus Administration: Wants to reduce navigation-related complaints

Preconditions:
- User has installed and launched the mobile application
- User location services are enabled
- Campus map data is available (cached or online)

Postconditions:
- User receives turn-by-turn navigation to destination
- Route is displayed on interactive map
- Navigation session is logged for analytics

Main Success Scenario (Basic Flow):
1. Student opens the Smart Campus Navigation System app
2. System retrieves student's current GPS location
3. Student enters destination (e.g., "Engineering Building Room 305") in search bar
4. System validates destination and confirms selection with student
5. System calculates optimal route considering current location, walkways, building entrances
6. System includes "Calculate Route" use case to determine path
7. System displays route on map with estimated walking time
8. System provides turn-by-turn navigation instructions (visual and optional audio)
9. Student follows instructions and walks toward destination
10. System updates route in real-time based on student movement
11. Student arrives at destination
12. System confirms arrival and ends navigation session

Extensions (Alternative Flows):

3a. Student selects destination from class schedule instead of searching
   3a1. System displays upcoming classes
   3a2. Student selects next class
   3a3. System auto-fills destination from schedule database
   3a4. Continue with step 5

5a. Student has accessibility preferences enabled
   5a1. System applies accessibility constraints (step-free route)
   5a2. System prioritizes elevators and ramps
   5a3. Continue with step 6

9a. Student deviates significantly from route
   9a1. System detects location divergence (>20 meters)
   9a2. System recalculates route from new position
   9a3. System displays updated instructions
   9a4. Continue with step 9

Special Requirements:
- Route calculation must complete within 3 seconds (NFR1)
- Indoor positioning accuracy within 3 meters (NFR6)
- Navigation instructions must be screen-reader compatible (NFR4)

Frequency of Occurrence: 
5-10 times per student per day during academic semester

USE CASE 2: RECEIVE NOTIFICATIONS

Title: Receive Notifications

Primary Actor: Student

Stakeholders and Interests:
- Student: Wants timely alerts about schedule/room changes
- Faculty: Wants to communicate last-minute changes effectively

Preconditions:
- Student is authenticated in the application
- Student has granted notification permissions
- Student's schedule is integrated with university system
- Campus Information System has triggered an event

Postconditions:
- Student receives and acknowledges notification
- Notification is logged in message history
- If room change occurred, student's next navigation automatically updates

Main Success Scenario (Basic Flow):
1. Campus Information System detects a room change event for student's upcoming class
2. System triggers notification to all affected students
3. Notification Service receives event data and formats message
4. Notification Service pushes message to student's mobile device
5. Student's phone displays notification with room change details
6. Student taps notification to open app
7. App displays detailed information: old room, new room, reason, time
8. Student acknowledges notification
9. App updates student's schedule with new room location
10. App offers to start navigation to new room
11. Student accepts navigation offer
12. System extends to "Navigate to Location" use case

Extensions (Alternative Flows):

5a. Student is currently navigating to old room
   5a1. System displays high-priority alert overlay
   5a2. System pauses current navigation
   5a3. Student acknowledges alert
   5a4. System automatically recalculates route to new room
   5a5. Continue with step 9

5b. Student does not respond to notification within 5 minutes
   5b1. System sends follow-up notification with increased urgency
   5b2. System displays banner when app is next opened
   5b3. Continue with step 6 when student interacts

11a. Student declines navigation offer
    11a1. System saves updated schedule
    11a2. Navigation not started
    11a3. Use case ends

Special Requirements:
- Notifications must be delivered within 30 seconds of event trigger
- Must support multiple notification types: room changes, events, emergencies
- Must be compatible with OS-level notification accessibility features

Frequency of Occurrence: 
2-3 times per student per week

USE CASE 3: SEARCH CAMPUS FACILITIES

Title: Search Campus Facilities

Primary Actor: Visitor

Stakeholders and Interests:
- Visitor: Wants to quickly find specific buildings or services without prior campus knowledge
- Campus Administration: Wants to provide positive visitor experience to support recruitment

Preconditions:
- Visitor has launched app (guest mode, no authentication required)
- Campus map database is accessible

Postconditions:
- Visitor receives search results with relevant locations
- Selected location details are displayed
- Option to navigate to location is available

Main Success Scenario (Basic Flow):
1. Visitor opens Smart Campus Navigation System app
2. System loads in guest mode (no login required)
3. System displays campus overview map with search bar
4. Visitor enters search query (e.g., "library", "parking", "admissions office")
5. System searches location database by name, keywords, tags, and aliases
6. System returns ranked search results (5-10 locations)
7. System displays results as list with thumbnail images and brief descriptions
8. Visitor taps on "Main Library" search result
9. System displays detailed information: full name, hours, photo, amenities
10. System shows location marker on map
11. Visitor taps "Navigate Here" button
12. System includes "Navigate to Location" use case
13. Visitor receives turn-by-turn directions to library

Extensions (Alternative Flows):

6a. Search returns no results
   6a1. System displays "No results found" message
   6a2. System suggests similar search terms or popular destinations
   6a3. Visitor modifies search query
   6a4. Return to step 5

6b. Search is ambiguous (multiple similar results)
   6b1. System displays all matching locations with disambiguating information
   6b2. System shows all results on map with numbered markers
   6b3. Visitor selects specific result
   6b4. Continue with step 9

11a. Visitor wants more information before navigating
    11a1. Visitor explores additional tabs: hours, contact, photos
    11a2. Visitor reviews location details
    11a3. Visitor returns to map view
    11a4. Continue with step 11 or close details

Special Requirements:
- Search must return results within 2 seconds
- Must support fuzzy matching and common misspellings
- Must include category filters (buildings, parking, dining, recreation)
- Guest mode must not require authentication (FR10)

Frequency of Occurrence: 
Peak during campus tours and orientation events; 50-100 searches per day per tour group

5. BUILDING

Attributes:

- isAccessible: boolean - Whether route is step-free

Operations:
- getNextWaypoint(): Returns next location in path

- getInstructions(): Returns turn-by-turn guidance

Relationships: 
- Created-by NavigationService

Key Responsibilities: Store waypoints, provide turn-by-turn instructions, calculate total distance/time

Attributes:
- segmentID: String - Unique segment identifier

- instruction: String - Human-readable direction (e.g., "Turn left at fountain")

Operations:
- getDirection(): Returns compass direction
- getLength(): Returns segment distance

Relationships: 
- Part-of Route (*:1)
- Connects Locations

Key Responsibilities: Provide directional guidance for one segment of journey


---

8. NAVIGATIONSERVICE

Purpose: Core service that calculates routes and provides real-time navigation

Attributes:
- currentRoute: Route - Active navigation route
- isNavigating: boolean - Navigation status

Operations:
- calculateRoute(start: Location, end: Location): Computes optimal path
- updateRoute(): Recalculates based on current position
- getCurrentPosition(): Returns user's real-time location
- provideGuidance(): Generates turn-by-turn instructions

Relationships: 
- Uses CampusMap
- Creates Route
- Interacts with User

Key Responsibilities: Pathfinding algorithm, real-time position tracking, guidance generation

9. CAMPUSMAP

Attributes:
- mapVersion: String - Version identifier for map data
- lastUpdate: DateTime - Timestamp of last map update

Operations:
- getMapData(): Returns geographic data

EXPLANATION (300 words):

Scenario: A student needs to navigate to their next class location using the Smart Campus Navigation System.

Participating Objects:
- Student (Actor): Primary user initiating navigation request
- Mobile App: Client-side application interface
- Navigation Service: Backend service responsible for route calculation and guidance
- Map Database: Data repository containing campus geographic information, building layouts, and pathways

Interaction Flow:

The sequence begins when the Student selects a destination, typically by searching for a location name or selecting from their integrated class schedule. This action triggers the Mobile App to send a "requestRoute(destination)" message to the Navigation Service.

Upon receiving the request, the Navigation Service must obtain current map data to perform route calculation. It sends a "getMapData()" message to the Map Database. The Map Database retrieves the relevant campus geography, including buildings, pathways, entrances, and accessibility features, and returns this data to the Navigation Service via the "map data" response.

With map data now available, the Navigation Service executes its pathfinding algorithm (likely A* or Dijkstra's algorithm adapted for pedestrian navigation). This algorithm considers factors such as current user location (GPS or indoor positioning), destination coordinates, available pathways and building entrances, elevation changes and stair locations, user's accessibility preferences if enabled, and estimated walking speed.

The algorithm produces an optimal route, which is returned to the Mobile App as "calculated route". This route object contains waypoints, turn-by-turn instructions, estimated time, and total distance. Finally, the Mobile App processes the route data and presents it visually on the interactive map, simultaneously displaying turn-by-turn instructions through the message "display navigation" to the Student.

Design Rationale: This sequence demonstrates separation of concerns—the Mobile App handles presentation, the Navigation Service manages business logic, and the Map Database provides data persistence. The synchronous communication pattern is appropriate here because the user expects immediate routing results (within the 3-second performance requirement from NFR1).

Alignment with Requirements: This sequence directly implements FR2 (calculate optimal routes) and FR4 (turn-by-turn navigation). The Map Database query supports FR11 (interactive map display).

EXPLANATION (300 words):

Scenario: A room change occurs for a student's upcoming class, and the system must notify the student immediately to prevent confusion and tardiness.

Participating Objects:
- Campus Information System (Actor): External university system that manages class schedules, room assignments, and events
- Notification Service: Backend service responsible for processing events and delivering notifications to users
- Mobile App: Client application that receives and displays notifications
- Student (Actor): Notification recipient

Interaction Flow:

The sequence is triggered by an event in the Campus Information System—in this scenario, a "roomChangeEvent" occurs. This might happen because classroom equipment failure requires moving class to different room, room double-booking detected requiring reassignment, instructor requests room change, or emergency requiring building evacuation.

The Campus Information System identifies all students enrolled in the affected class and sends a "roomChangeEvent" message to the Notification Service. This message contains class identifier (course code, section), old room location, new room location, reason for change (optional), time of change, and list of affected user IDs.

The Notification Service receives this event and performs several operations: validation (confirms event is legitimate and complete), recipient filtering (determines which users should receive notification), prioritization (marks as high-priority if class is imminent within next 2 hours), message formatting (creates user-friendly notification text), and delivery (sends push notification via platform-specific channels).

The Notification Service sends a "push notification" message to the Mobile App. Modern mobile operating systems queue these notifications and deliver them even if the app is not actively running. When delivered, the Mobile App displays the notification to the Student through system notification UI. The Student sees a banner or alert with the notification message. The Student taps the notification, which opens the Mobile App and displays detailed information through "display notification". After reviewing, the Student sends an "acknowledge" message back to the Mobile App.

Design Rationale: This sequence implements the publish-subscribe pattern where the Campus Information System publishes events, and the Notification Service subscribes to relevant events for processing.

Alignment with Requirements: This sequence implements FR6 (send push notifications about schedule changes) and directly addresses Problem 2 (lack of real-time facility information).
